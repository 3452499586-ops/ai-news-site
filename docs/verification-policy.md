# 核验规范

<a id="verification-levels"></a>
## 核验等级（verification-levels）

### 已核验 `verified`

官方原始材料与独立来源相互支持；或正式文档、发布页与公开仓库相互支持；或政府、论文、标准机构的正式资料能够直接证明。该状态表示事件本身已获支持，不代表本站复现了厂商的全部性能数字。

### 官方声明 `official`

信息确由相关机构发布，但缺少独立确认，或核心数字只能由机构自己提供。正文必须使用“根据该机构的官方声明”等限定表达。适用于厂商自报性能、用户数、未来计划、安全能力和合作效果。

### 待确认 `pending`

信息仅来自单一社交账号、匿名消息、不可访问原始链接、非官方截图，或多个来源相互冲突。待确认内容不得进入正式 5—8 条精选；需要观察时应另行保存，不在当前页面当作事实展示。

<a id="dual-source"></a>
## 双源规则（dual-source）

融资、收购、人事变动、监管决定、安全事故和重大争议至少需要“原始官方材料 + 一个独立权威来源”。厂商与其合作伙伴双方公告可以加强确认，但若两者共同发布同一口径，仍应谨慎区分其与独立媒体核验的差别。

若不同来源存在差异，应在 `uncertainty` 中明确写出分歧，不得自行选择更吸引人的数字。无法解决的关键冲突应降为待确认并移出正式精选。

## 每条资讯核查清单

- 机构、模型和产品版本名称是否准确。
- 是正式发布、预览、测试、计划，还是仅宣布未来可用。
- `eventTime`、`publishedTime`、`verifiedTime` 是否分别对应事件、来源发布和本站核验时间，且包含时区。
- 金额、百分比、用户数、跑分是否能在来源中逐字定位，是否属于厂商自报。
- 开源状态是否有具体许可证支持；“可下载”不自动等于开源。
- API 是否真正开放，以及账户、地区、套餐和预览资格限制。
- 原始链接是否仍可访问，文章是否后来更新、撤回或更正。
- 是否是旧新闻重新传播，标题是否把计划误写成已完成。

## 表述与纠错

摘要用中文重新组织，不大段复制原文。事实、官方说法和本站判断要分开。每次实质性修正都在 `corrections` 中记录日期、旧表述、改后表述和原因；仅改错别字可以不记。发现核心事实错误时，先从页面移除该条，再完成重新核验。
